# 轻量性能优化与验证记录

验证日期：2026-09-08。基线为 `330f61bd68f9a2ceb909524d514a0f1fe0eb2a24`；优化版本为本分支。保留 Tauri 与原生 JavaScript、全部卡片 DOM、原项目 JSON 必填字段及原图。

## 已实现

1. 保存：编辑修订号与已保存修订分离，旧响应只确认提交时的修订；保存中新增编辑继续排队。备注保持 280 ms 防抖。失败向调用方传播并保留脏状态，关闭、切换、导入前刷新失败会阻止后续操作。
2. 缩略图：512 像素 PNG、不放大、保留透明度、GIF 首帧。系统应用缓存目录独立存储，键包含规范化路径、文件大小、修改时间和算法版本；临时文件重命名完成写入。同图请求去重、最多两个生成任务。512 MB 软上限按文件最近使用时间清理，租约保护正在使用的缓存；清理最多每 30 秒在后台执行一次。
3. 渲染：轨道、卡片 ID 映射与局部更新；备注不触发卡片重建。纵向轨道与横向卡片分别由 IntersectionObserver 判断可见性，预加载一屏，折叠轨道不发起新请求。离屏卡片释放图像及缓存租约；失败显示可重试占位。对比原图节点按身份复用，状态修改保留缩放和平移；过期预览回调忽略。滚轮、平移和尺寸更新使用 requestAnimationFrame 合并。
4. 导入：三个入口统一增量返回 `{projectPath, updatedAt, image}`，文件与网络工作在 Rust 阻塞任务中执行。批量顺序导入、持续进度、取消后不启动下一项；成功部分保留并作为一次撤回，结束时重读完整项目校准。导入前必须保存成功，期间暂停编辑与切换，保留浏览和取消。缩略图按可见性另行排队，失败不回滚原图。

内部新增 `get_image_thumbnail`、`release_image_thumbnails`、`reload_project_command`，桥接层同步更新。缩略图输入沿用项目路径范围校验。固定 image 0.25.10、avif-decode 1.0.2；PNG/JPG/JPEG/WebP/GIF/BMP/AVIF 均实测。输入限制 100 MB、单边 8192 像素；image 解码分配预算 512 MB（库的尽力限制），AVIF 的 libaom 在解码前限制尺寸。网络连接/读取/总超时分别为 10/30/120 秒。

## 测量方法

同一台 Windows 10 Pro 19045、Intel Core i9-9900K（8 核 16 线程）、约 32 GiB RAM，WebView2/Edge 152；两版均 Release 构建。使用固定随机种子的 200 张 JPEG、10 条轨道，每轨 20 张，尺寸为 2560×1440 或 3840×2160。透明图、动图、AVIF、损坏文件另做真实桌面集成验证，不将它们的格式测试等同于性能测试。

基准版本使用独立应用标识、数据目录及调试端口，自动打开生成的测试项目。计时从调用打开项目开始，到首屏可见卡片图像加载完成；随后逐轨横向滚动，记录 requestAnimationFrame 间隔。内存每 100 ms 采样应用进程及其子进程 RSS 总和，统计打开和全项目浏览阶段峰值。RSS 求和可能重复计入共享页，不能视为私有内存；两版使用同一口径。测试未关闭其他桌面程序，第三轮优化版出现较大启动波动，仍保留结果。

## 验收结果与限制

- 热缓存首屏中位数 1097.3 → 573.1 ms，缩短 **47.8%**。三轮均小于 1 秒，但 **至少 50% 的改善目标尚未达成**，不能标为全部性能验收通过。
- 全项目浏览进程树内存峰值中位数 1393.5 → 672.1 MiB，下降 **51.8%**，超过 40% 目标。浏览结束保留 200 张卡片 DOM，加载图像由 200 降为 24。
- 优化版三轮滚动 P95 均不超过 20.5 ms，最长 66.6 ms，无超过 200 ms 的滚动帧。启动阶段另有 355–565 ms 的最长帧，未计入滚动指标；启动仍有进一步优化空间。
- 冷缓存首屏缩略图约 1.31 秒完成，打开 IPC 4.8 ms、同步渲染 12.4 ms。先建立占位界面，再异步加载首屏，不等待全部 200 张图片生成；同步渲染时长不等同于首次可交互绘制时间。
- 50 张导入、进度、编辑锁、浏览相关图像复用、取消和部分失败通过桌面集成验证；保存竞态和失败关闭通过回归测试。网络超时参数已检查，未进行 120 秒真实超时的计时验收。
- 本次记录的是最终集成版本与原始版本的对比；没有四个阶段各自独立的性能样本，因此不能量化单一阶段的贡献。没有引入完整虚拟列表；后续优先分析启动长帧和缩略图首屏调度，并扩大样本轮数，再决定是否需要虚拟列表。

[PR #1：修复自动保存覆盖与轨道目录冲突，优化图片列表性能](https://github.com/Star-Fish-C/Image-rail/pull/1)，审阅头提交 `05c8cd8294d7b0c8a50b2dccdb5b1951d5d45598`。其 11 项前端测试单独运行通过。已整合轨道字母/目录唯一分配（包含旧目录、大小写及 T27 等情况）、轨道映射、打开项目错误处理和明确的 npm 测试路径。

PR 仍有一处保存失败漏洞：粘贴图片入口等待刷新，但保存函数吞掉写盘异常，导入随后基于旧磁盘项目继续，覆盖未保存备注。对该提交的复现结果为保存失败后仍导入 1 张、备注回到旧值。本分支通过保存异常传播与统一导入入口修复，并在真实桌面测试中验证保存失败时导入调用为 0、备注保留。PR 的原图 lazy loading 由本分支独立缩略图方案替代；快照保存由修订号调度替代。本地整合不代表远程 PR 已合并。

## 复现

从仓库根目录运行，确保 CMake、NASM、Perl 在 PATH 中，另准备 Python 的 Pillow（含 AVIF）、psutil，以及 Node 的 playwright 模块。可通过 `NODE_PATH` 指定测试用 Node 模块目录、`IMAGERAIL_PYTHON` 指定 Python 可执行文件。

```powershell
npm test
cargo test --manifest-path src-tauri/Cargo.toml
python scripts/make-perf-fixtures.py
./scripts/build-benchmark.ps1 baseline
./scripts/build-benchmark.ps1 optimized
node scripts/native-benchmark.cjs baseline baseline-run
node scripts/native-benchmark.cjs optimized optimized-run
node scripts/native-benchmark.cjs optimized integration
```

脚本仅操作 `.perf` 中的生成数据与隔离测试应用。每轮使用不同标签保留结果；测热缓存前先完整浏览一次。正式发布应清除 `TAURI_CONFIG` 后重新构建，不能分发 `.perf` 内含测试调试端口的可执行文件。
